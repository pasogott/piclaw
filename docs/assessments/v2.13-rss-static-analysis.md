# Piclaw v2.13 RSS static analysis

The v2.13.0 release did not add runtime code. The observed RSS growth has two earlier or workload-dependent causes: Earendil 0.84 increased the cold module graph by about 32 MiB, and each concurrently active chat retains a complete session/resource graph.

Assessment date: 7 August 2026

Scope: source analysis and existing measurements only. No production restart, forced eviction, synthetic load or runtime mutation was used.

## Release delta

The deployed source delta from `eddab112fba832583758ef7a267b5626d28dd12d` to v2.13.0 `48d55c5308726c00b804bb1cadcbc92755d69858` changes:

- `VERSION`
- `package.json` version
- `tests/e2e/setup/README.md`
- `tests/e2e/setup/configure-test-instance.ts`

`runtime/src` changed in zero files. The v2.13 release cannot explain a new runtime allocation path.

## Cold-start shift

The cold-start break occurs at the Earendil 0.83 to 0.84 deployment.

| Population | Samples | Minimum | Median | Maximum | Mean |
|---|---:|---:|---:|---:|---:|
| Last 20 pre-0.84 starts | 20 | 132,595,712 | 155,295,744 | 164,122,624 | 152,935,834 |
| 0.84 starts | 2 | 184,815,616 | 188,850,176 | 188,850,176 | 186,832,896 |

Median increase: **33,554,432 bytes (32 MiB)** with zero cached sessions and zero active chats.

Earendil package graph changes support this attribution:

- coding-agent root graph: 166 to 173 modules; +59,061 source bytes;
- agent-core root graph: 32 to 40 modules; +9,473 source bytes;
- coding-agent adds `grok-mermaid`, `pi-client` and `pi-protocol`;
- agent-core adds `pi-telemetry`;
- TUI exports and Markdown/LaTeX/fullscreen modules expand;
- interactive mode now imports the Mermaid transformer, which imports `grok-mermaid`.

Piclaw imports `@earendil-works/pi-coding-agent` from the package root in 99 runtime source lines and `pi-ai` in 37. The root entry exports `main`, interactive modes, TUI components and themes. ESM export graphs evaluate referenced modules, so a headless web process can load CLI/TUI dependencies without starting the TUI.

The package export map exposes only:

- `.`
- `./client`
- `./rpc-entry`

Piclaw cannot replace broad root imports with supported headless/core subpaths today. Deep `dist/*` imports would create a brittle private dependency. Earendil should expose a supported core/session/model entrypoint before Piclaw narrows these imports.

The 32 MiB increase cannot be attributed byte-for-byte from source size. Module initialisation, JIT/code pages, provider SDKs, native bindings and allocator arenas contribute. The timing and zero-session snapshots establish the 0.84 cold graph as the cause class.

## Per-session ownership

`AgentPool` caches one `AgentSessionRuntime` per chat JID. Each runtime owns:

- an Earendil `SessionManager`;
- an Earendil `AgentSession` and `Agent`;
- a `DefaultResourceLoader`;
- an extension runner and extension runtime;
- per-session tools, handlers, commands and prompt maps;
- channel-specific prompt appendices and session bindings.

### Transcript state

`SessionManager` retains:

- `fileEntries`: every parsed JSONL entry;
- `byId`: an index of entries by ID;
- label and timestamp maps;
- the active leaf.

`Agent.state.messages` contains the compaction-aware active message list. Ordinary message objects are referenced from session entries rather than deep-copied, but the additional arrays, maps and generated summary/custom messages still add structural memory.

Three active session files observed during the investigation contained:

- 18.6 MiB of JSONL;
- 4,353 parsed entries;
- about 5.21 million message/thinking characters;
- about 1.43 million tool-argument characters.

JSON text expands into objects, arrays, strings and map entries. Loading also creates temporary chunk and line strings. Bun can retain allocator pages after those temporaries become unreachable.

### Resources and extensions

Every session constructs and reloads a separate `DefaultResourceLoader`. Each loader retains:

- extension objects and runtime;
- skills and diagnostics;
- prompts and diagnostics;
- themes and diagnostics;
- AGENTS/context files;
- package/resource metadata maps;
- path and source-info maps;
- system and append prompts.

Piclaw supplies 28 built-in extension factories for every session, plus MCP and a per-chat SSH extension. Static Piclaw source contains 41 `registerTool` calls and 45 extension event-handler registrations. The workspace contains 129 installed add-on manifests and 37 skills.

Earendil caches imported extension **factory functions**, but each session runs those factories again and builds fresh extension objects, handler maps, tool maps and runtime closures. `AgentSession` then builds additional tool registries, definitions, snippets and guidelines.

`AgentSession.dispose()` invalidates the extension runner, aborts work, disconnects listeners and clears its external event-listener array. It does not explicitly clear `SessionManager.fileEntries`, resource-loader arrays/maps or extension/tool maps. Removing the runtime from the pool makes these objects eligible for garbage collection, but native/allocator RSS may not return immediately.

## Cache and eviction policy

Normal defaults:

- main session pool maximum: 1;
- main idle TTL: 180 seconds;
- side idle TTL: 60 seconds;
- cleanup interval: 30 seconds;
- memory-pressure threshold: 384 MiB RSS;
- pressure idle TTL: 60 seconds;
- pressure pool maximum: 1.

Production overrides the threshold:

```text
PICLAW_MAIN_SESSION_PRESSURE_RSS_BYTES=536870912
```

This raises activation from 384 MiB to 512 MiB. At observed RSS between 400 and 450 MiB, the code default would enable pressure mode, trim eligible idle sessions, call `shrinkDatabaseMemory()`, and run `Bun.gc(true)`. The production override prevents that path.

The pool maximum is not a hard cap for active work:

- `runAgent()` holds reference-counted eviction protection for the whole turn;
- streaming, bash-running and compacting sessions are retained;
- pool-limit eviction excludes protected or active sessions.

Three concurrent streaming chats therefore retain three full session/resource graphs even when the configured pool maximum is one. This is correct for safety; eviction must not invalidate active turns.

## Current evidence

Existing v2.13 evidence initially showed no continuous growth during the release observation window. Later RSS increases coincided with loading a second and then third active chat.

At one captured point:

- cached main sessions: 3;
- active chats: 3;
- process RSS: about 452 MB;
- heap used: about 124 MB;
- external memory: about 83 MB;
- no recovery, OOM or service errors.

The previous v2.12.12/Earendil 0.84 process already used about 252–263 MB cgroup memory with this large chat loaded. This confirms that loaded-session memory predates v2.13.0.

## Cause ranking

1. **Measured primary cold cause:** Earendil 0.84 eager package/module graph, +32 MiB cold RSS.
2. **Measured primary workload cause:** multiple concurrently active full session/resource graphs.
3. **Policy amplifier:** production's 512 MiB pressure threshold delays idle cleanup and forced GC relative to the 384 MiB code/default documentation.
4. **Probable retention amplifier:** Bun/native allocator pages retained after large JSONL parsing, context construction and extension initialisation.
5. **Excluded cause:** v2.13.0 runtime code; there is no runtime source delta.

No static evidence establishes a continuously growing leak. Exact per-session or per-module byte attribution requires heap/native allocation profiles and was outside the static-analysis scope.

## Safe actions

### Deployment configuration

Remove `PICLAW_MAIN_SESSION_PRESSURE_RSS_BYTES=536870912` from the service environment, or set it to the reviewed default `402653184`.

This change affects only idle/eligible cleanup. Active-session protection remains intact.

### Instrumentation

Add structured create/dispose metrics per session:

- JSONL bytes and parsed entry count;
- active context message count and estimated serialized characters;
- skill, extension, tool, command and handler counts;
- resource metadata and context-file bytes;
- RSS, heap, external and cgroup memory before create, after create, before dispose, after dispose and after forced GC;
- disposal duration and whether references remain in pool/in-flight maps.

Expose these fields in the existing runtime memory snapshot. This permits attribution without collecting message contents.

### Session/resource design

Investigate:

- sharing immutable skill, prompt, theme and context-file manifests between sessions;
- sharing extension module/factory discovery while retaining per-session extension state;
- explicitly clearing large arrays/maps on session disposal before dropping the runtime;
- verifying `trimPreCompactionEntries()` reduces current files after compaction;
- avoiding full resource reload for sessions whose workspace/resource fingerprint is unchanged.

### Earendil packaging

Request supported subpath exports for headless/core use. Piclaw should then replace broad root imports with narrow model/session/tool entrypoints. Do not use private `dist/*` paths as a workaround.

## Threshold semantics

Keep two separate gates:

- **cold-start gate:** measured immediately after web startup with zero cached sessions;
- **loaded-session observation:** reported by number of cached/active sessions and their entry/context/resource counts.

A single fixed RSS ceiling cannot fairly cover both an empty process and multiple protected large sessions. Cold-start RSS remains the release regression gate. Loaded-session memory should use per-session accounting, a pressure threshold and a no-continuous-growth condition.
